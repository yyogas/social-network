## 3. États consommateur et règles de priorité proposées

Ces propositions précisent le comportement attendu de C-IDENTITY ; elles ne modifient pas le DTO ou les états serveur. Accord Backend/Sécurité demandé avant intégration. Les noms sont locaux au client.

| État ou observation | Affichage et transitions proposées |
| --- | --- |
| VERIFYING | Masquer les données privées ; montrer « Vérification de votre session » ; lecture courante unique ou réponses ordonnées ; aucune transition sur résultat d'une génération locale abandonnée. |
| 200 anonymous valide | ANONYMOUS ; vider données privées du contexte courant, proposer connexion. Si intention logout en attente : conserver son absence de confirmation, ne pas annoncer un effet non prouvé. |
| 200 authenticated valide | AUTHENTICATED ou RESTRICTED selon account_state ; capacités reconnues seulement. Charger profil/paramètres séparément ; panne de profil n'est pas panne d'identité. Priorité au verrou logout éventuel et à la vérification de transition B01/B02. |
| UNAVAILABLE | Aucun droit inventé ; privé masqué, message neutre et bouton Réessayer après budget. Ne pas détruire la session ni promettre sa révocation. Le signal d'indisponibilité n'est pas enregistré comme déconnexion analytics. |
| Intention logout créée | Invalider les requêtes/vues privées de l'intention courante avant attente réseau ; purger caches dérivés et formulaires du compte quitté. Prévenir les autres onglets comme signal d'invalidation, sans leur envoyer identité/secrets ; mécanisme et portée B03/A02 à ratifier. |
| LOGOUT_UNCONFIRMED | « Vos données sont masquées ici. La déconnexion du serveur n'est pas confirmée. » ; reprise de la même intention seulement si liaison/version valides. Relecture positive de A ne lève pas seule le verrou ; 049 anonymous n'est pas reçu d'effet. |
| 204 correspondant au logout courant | Annoncer révocation de cette session navigateur selon le contrat, jamais de tous les appareils. Ancien 204 A reçu dans le contexte B : ne pas vider B. |
| Changement de compte détecté | Abandonner les anciennes vues et écritures en attente d'envoi, invalider les réponses liées à A ; afficher une étape neutre de reprise du contexte, sans importer un brouillon A vers B. Les écritures A déjà envoyées gardent un résultat potentiellement inconnu, jamais rejoué sous B. |
| Cookie tardif / identité non attribuable | Revenir à état sûr, vérifier selon le protocole ; si perte d'accès constatée, proposer connexion explicite. Aucun fallback vers A, aucun maintien affirmé de B, aucune demande de lecture de cookie HttpOnly côté JS. |

Priorités : invalidation de contexte connue et verrou logout priment sur succès d'une lecture ; une réponse ancienne est ignorée qu'elle contienne succès, erreur ou anonyme. Une séquence locale sert à ordonner les réponses, pas à prouver la génération serveur ou à empêcher les effets de Set-Cookie. Une annulation fetch n'annule pas un commit.

Clavier/lecture assistée : statut annoncé sans déplacement répété du focus ; bouton de reprise accessible, pas de boucle de soumission ; si une vue privée est retirée, placer le focus sur un titre neutre stable. Effacer les anciens messages comportant du contenu privé. Libellés proposés à 02/16, langues encore ouvertes. Ne pas recopier le DTO, l'identité saisie, K, la preuve CSRF ou les challenges en logs/analytics.

## 4. Mapping des erreurs et reprises proposé au producteur

Appliquer d'abord le contrôle du contexte local et de l'opération : une réponse ancienne ne doit déclencher ni déconnexion ni retry dans le nouveau contexte. HTTP seul ne suffit pas. Tous les codes ci-dessous sont ceux du delta examiné, pas de nouveaux codes serveur créés par 05.

| Réponse / opération | Comportement Web attendu | Action ou arrêt |
| --- | --- | --- |
| 401 AUTH_INVALID, login | Refus du formulaire, texte neutre | Aucune déconnexion générale ; nouvelle saisie explicite, pas de retry automatique login |
| 401 PREAUTH_CONTEXT_REQUIRED / PREAUTH_CONTEXT_EXPIRED | Arrêter l'opération préauth ; contexte à rétablir | Préparation explicite, jamais rejeu transparent d'une preuve possiblement consommée |
| 401 AUTH_REQUIRED, route protégée courante | Masquer la vue concernée et vérifier identité courante | Ne pas confirmer logout ; préserver état incertain si mutation envoyée ; ancien 401 A n'affecte pas B |
| 403 REQUEST_ORIGIN_DENIED / CSRF_INVALID | Arrêter mutation, message sûr sans détails secrets | Pas de boucle de refresh/renvoi ; acquisition de preuve valide et nouvelle action seulement selon contrat, pas auto-relogin |
| 403/404 sur objet | Objet indisponible/refusé | Ne pas déconnecter un contexte valide ; 004 absent dans l'option sans refresh ne déclenche aucune tentative de renouvellement |
| 409 AUTH_CONTEXT_CHANGED | Arrêter l'intention liée à l'ancien contexte, retirer ses vues | Relire contexte cohérent ; pas de DELETE de /current avec nouvelle génération pour terminer A |
| 409 IDEMPOTENCY_CONFLICT | Opération non réexécutée, état précédent non dévoilé | Ne pas « réparer » en générant K ; vérifier intention et suivre procédure explicite |
| 409 OPERATION_IN_PROGRESS | Montrer en cours, non succès/échec final | Même tuple après Retry-After si contexte/fenêtre/budget toujours valides |
| 409 OPERATION_RECONCILIATION_REQUIRED | Résultat non réconcilié | Arrêter retries ; procédure explicite du producteur, pas de succès ni rollback présumé |
| 409 CHALLENGE_CONSUMED | Preuve déjà utilisée pour cette nouvelle consommation | Ne pas conclure que la connexion ou récupération courante a réussi ; suivre la voie d'accès/récupération autorisée |
| 410 CHALLENGE_EXPIRED / 400 CHALLENGE_INVALID | Preuve non utilisable ; message de formulaire | Nouvelle procédure explicitement choisie, pas changement automatique de clé ; 400 syntaxique corrige les champs |
| 429 RATE_LIMITED | Attente accessible, pas de compte à rebours qui soumet seul | Respecter Retry-After ; s'il dépasse budget/fenêtre, arrêter et proposer reprise manuelle après délai |
| 503 AUTHORITY_UNAVAILABLE / CONTEXT_UNAVAILABLE, timeout, réponse illisible | UNAVAILABLE pour lecture ; résultat inconnu si mutation a pu être appliquée | Reprise lecture/replay sûr bornée ; ne pas transformer panne en anonyme ni relancer login automatiquement |

Une reprise manuelle signifie nouvelle action volontaire, pas réinitialisation des compteurs de quota, du contexte ou de la fenêtre K par commodité. L'oracle d'une opération déjà committée reste son reçu autorisé ou la procédure producteur ; un état anonyme ne prouve pas rétroactivement le logout demandé.
